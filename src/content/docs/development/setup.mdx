## 現在のチェックアウト

このチェックアウトは公式`create-zudo-doc@5.27.0`で初期化済みで、生成されたフレームワーク設定、`package.json`、`pnpm-lock.yaml`を含む。現在の依存はzudo-doc 10.0.3・zfb 6.0.1系で、scaffoldは`create-zudo-doc@10.0.3`と照合済み（2026-11-12）。Node.js 24以上とpnpm 10.30.3を用意する。2026-11-12の確認環境はNode.js 24.22.1、pnpm 10.30.3。

新しいチェックアウトでは、リポジトリのルートから次を実行する。

```sh
pnpm install --frozen-lockfile
pnpm check:docs
pnpm check:assets
pnpm test:setup
pnpm build
pnpm dev
```

`pnpm install --frozen-lockfile`は追跡中のlockfileと依存定義が合わない場合に停止する。`pnpm dev`が表示するURLをブラウザーで開く。2026-09-24の初回`pnpm build`は44ページ、41文書ルートと検索項目、47公開資産を生成した。現在のページ数は文書の追加で変わるため、`pnpm build`の表示と`project/validation/static-check.json`で確認する。

初期の文書のみのスナップショットではnpmレジストリの名前解決が`EAI_AGAIN`となり、初期化とビルドを確認できませんでした。その後2026-09-24に公式scaffolderとlockfileによる導入を完了しています。これは当時の記録で、現在の実行結果ではありません。

## 文書のみのスナップショットを初期化する場合

`node scripts/setup.mjs`は、公式scaffoldをまだ取り込んでいない文書のみのスナップショットで使う一回限りの補助スクリプト。この初期化済みチェックアウトでは実行しない。公式scaffolderを一時フォルダーで実行し、MDX、設定、画像、設計資料を保護して土台を取り込む。衝突があれば上書きせず停止する。依存導入はscaffold取り込みの後に別途行う。

## バージョンを指定する

`scripts/setup.mjs`の既定版は`10.0.3`（初期化時は`5.27.0`）。別版を試す場合は動作確認した版を明示する。

```sh
ZUDO_DOC_CLI_VERSION=確認したバージョン node scripts/setup.mjs
```

実際のコマンド・生成された依存情報は`.handoff/setup-record.json`へ記録する。npmへの接続が必要なのはローカルの初期化とインストール時。3D単体HTML自体は外部通信なしで開ける。

## 手動で初期化する場合

```sh
pnpm create zudo-doc zudo-case-doc-site --lang ja --no-i18n --no-git --no-install --yes
```

生成先のスターター記事を確認してから、このセットの`src/content/docs/`、`public/`、`zfb.config.ts`を移す。`engineering/`、`project/`、`AGENTS.md`は作業資料として同じリポジトリへ入れる。既存サイトへ混ぜる場合はセットアップスクリプトを使わず、記事と設定を意図的に統合する。

## 表示確認と公開前の注意

2026-09-24のChrome 146.0.7680.153でdesktop 1440×900、narrow 390×844を確認した。41文書ルートと8カテゴリが両幅で表示され、narrowでは横はみ出しがなかった。検索・テーマ・画像・R8/R6プレビューの操作も確認済み。経路別の結果、非空ダウンロード、画面記録はリポジトリの`project/browser-validation.md`にまとめる。ビルドやブラウザーの表示確認は、嵌合・強度・運搬などの現物試験を代替しない。

Cloudflareでは`zudo-case.zudolab.dev`を文書・Asset Viewer・根拠ファイルに、`zudo-case-preview.zudolab.dev`を単体プレビュー・参照/旧版ZIPに使う。`pnpm build`後に`pnpm prepare:worker-assets`を実行して２つの配信フォルダーを作る。GitHub Actionsは`main`へのpushでプレビュー、文書の順にデプロイする。ただし最終コミットメッセージに`[skip deploy]`があるpushはデプロイジョブをスキップする。`[skip ci]`とは異なり検査は維持する。文書更新そのものをデプロイの許可とは扱わない。`noindex`は有効にしているが、アクセス制御ではない。旧ソースZIPや見積画像もURLを知る人は閲覧できる。

このセットはルートパス配信を想定。サブパス配信に変える場合は、iframeと画像/ダウンロードのURLも確認する。

公式：[Installation](https://zudo-doc.takazudomodular.com/docs/getting-started/installation/)、[CLI](https://zudo-doc.takazudomodular.com/docs/reference/create-zudo-doc/)、[設定API](https://zudo-doc.takazudomodular.com/docs/guides/configuration/)。

## ローカルと本番のプレビュー確認

`pnpm dev`で開いた文書のR8/R6プレビューと参照・旧版ZIPのリンクは、既定では同じチェックアウトの`public/previews/`と`public/downloads/`を参照します。R8ページの埋め込み枠の下にある「表示元: ローカル (public/)」を確認してください。`public/previews/r8-simple-lid.html`を変更すると、開き直したローカル文書からその変更を確認できます。

別のプレビュー配信元を試すときは、起動時にHTTP(S)のoriginだけを指定します。パスは付けません。次の例のホストは、実際のローカル配信先へ置き換えてください。

```sh
ZUDO_CASE_PREVIEW_ORIGIN=http://preview.example.test:8787 pnpm dev
```

`dev`・`check`・`build` は同じチェックアウトで併用できます。起動ごとに `.cache/site-runs/run-*` の独立した設定と内部キャッシュを使うため、別コマンドを実行しても稼働中のdevの表示元は変わりません。異なるoverrideを指定したdevも、`pnpm dev --port 3001` のように別ポートで起動できます。記事・コード・設定は実行ごとのコピーを使い、devでは元の編集・追加・削除を約250ms間隔で反映します。`public/previews/` と `public/downloads/` は元のチェックアウトを直接参照します。`public/assets/` は zfb 4.5.0 で見つかったdev配信制限（zudo-front-builder#4233）の回避として、実行ごとの内部資産領域へ同期します。zfb 6.0.1でもこの同期を維持しています。設定を編集すると、同じ表示元とポートでネイティブdevプロセスを再起動します。build/checkは起動時のコード・設定コピーを使います。

内部キャッシュは終了時に削除します。強制終了などで残った実行フォルダーは、対応するプロセスが停止していることを確認してから削除してください。公開ビルドは従来どおりチェックアウトの `dist/` に出力し、`pnpm preview` もその出力を配信します。buildは `.cache/site-build.lock` で直列化し、同時の２件目をエラーで停止します。強制終了でロックが残った場合は、所有プロセスが停止済みと確認してから削除してください。

この場合は枠下に指定先のホストが表示されます。本番ビルドの既定値は`https://zudo-case-preview.zudolab.dev`で、文書とプレビューの２ホスト配信を維持します。本番ビルド前は上記環境変数を外してください。`pnpm build`後の`pnpm check:built-preview-links`で、生成した文書HTMLに本番ホストのリンクがあり、ローカルURLが混入していないことを確認できます。

## 依存・scaffoldの保守

現在のホストは zfb 6.0.1 / zudo-doc 10.0.3（history-server 10.0.3）、TypeScript 5.9を使います。外観はGraphiteで、`zfb.config.ts`と`setup.preset.json`の両方に`themePack: "graphite"`を明示しています（zudo-doc 10では`"default"`がGraphiteの別名になり、生成CLIは`"default"`を拒否するため）。zfb 6はesbuildを使わず、`ZFB_BUNDLER`・`ZFB_ROLLDOWN_PROTOTYPE`を設定するとすべてのzfbコマンドが停止します。`ZFB_ESBUILD_BIN`も読まれません。これらを環境に設定しないでください。トップページの図は`public/img/zudo-case-logo.svg`、リンク共有用カードは`public/img/ogp.png`です。`siteUrl`を設定したため、各ページの`canonical`と`og:url`も本番ホストを指します（`noindex`は維持）。編集元と再生成手順は`project/site-imagery/README.md`にあります。コピーした公式scaffoldの版・変更箇所・同期手順は `ZUDO_DEPS_PINS.md`、10.0.3更新の実行結果は `project/maintenance-zudo-doc-10.0.3.md`、9.1.2更新は `project/maintenance-zudo-doc-9.1.2.md`、6.2.0更新は `project/maintenance-120.md` を参照してください。`pnpm check:wind` と `pnpm check:preview-isolation` は非デプロイ検証です。後者はインストール済みの実CLIで別ポート・並行build/check・編集・設定再読込を検証します。新CLIのscratch/defineは使えますが、build/checkの入力スナップショットを維持するためmirrorを残しています。


## 公開配信の検証範囲

ローカルのモックテスト（`node --test tests/verify-deployed-assets.test.mjs tests/worker-assets.test.mjs`）は、短いサンプル資産でHTTP転送、SHA-256照合、Workerのチャンク欠落・切り詰めを確認します。デプロイ後のGitHub Actionsと`pnpm verify:deployed`は、対象２ファイルを全量GETでストリーム読み込みし、チェックアウト内の元ファイルとバイト数・SHA-256を照合します。HEADリクエストは到達確認だけです。どちらもブラウザー/WebGL表示の証拠ではなく、ブラウザー表示の確認はリポジトリの`project/browser-validation.md`を参照してください。

第三者ライブラリや元資料の著作権・ライセンス表示は元ファイルの記載に従います。資料整理によって再ライセンスしたものではありません。

## 再実行と復旧

`pnpm prepare:worker-assets`を同じビルド結果に対して再実行すると、世代番号と分割ファイルの完全性を確認してから「already prepared」と表示し、配信ファイルを変更せず終了します。不完全な分割ファイルや片方だけ残った入力が見つかった場合は停止します。`pnpm build`を再実行して入力を作り直し、改めて`pnpm prepare:worker-assets`を実行してください。準備中の失敗でも元の`dist/previews`と`dist/downloads`は移動せず、成功後にだけ配信用のコピーから除きます。`public/`や`engineering/`の元資料には触れません。
