金属ケース（3U60・7U40・7U60）の台帳を更新する保守担当向けの手順です。独立した家庭印刷、10BOX-v2、2WAYの仕様台帳には適用しません。編集方針は[文書・表・資産の更新](../development/maintenance.mdx)、設計の現状は[採用仕様とデータ状態](./status.mdx)を参照してください。

## 数字の更新

金属ケースの機種別ページ、比較表、BOMは`project/current-spec.json`から生成する。

```sh
node scripts/sync-reference-tables.mjs
node scripts/check-docs.mjs
```

台帳の数値はR6/R8の出力から読み取った値。CAD変更後に出力と照合して台帳を更新する。図面を変えずに台帳だけ変えて「製作済み」としない。生成対象ファイルの先頭コメントにも編集元を記載する。R9-PROTOTYPE-01の版・ファイル表は`scripts/sync-r9-doc-table.mjs`、R10一式のZIP・座金の表は`scripts/sync-fullset.mjs`が生成する。

## 見積・製作データの状態を進める

現在価格の欄（`current_total_jpy`・`current_lid_price_jpy`・`current_band_price_jpy`）は未見積・採用前なら`null`のままにする。対応する`current_*_scope`も`null`または省略とする。相見積を複数保存しても、採用するまで現在額を埋める必要はない。`0`は未確認の代用にしない。

`project/quote-records.json`へ現在版の見積を追加するときは、台帳全体で一意の空でない`id`、`kind`（`supplier_quote`または`user_quote_screenshot`）、`applies_to_current_release: true`、`component`（`total`・`lid`・`band`）、`model`または`models`の一方だけ、`revision`、正の整数の`quantity`、`price_basis`、`currency`、空でない`tax_status`、真偽値の`shipping_included`、リポジトリ内に実在する`source`を記録する。`price_basis`は`total_jpy`が１台あたりなら`per_unit`、対象数量分の合計なら`lot_total`。`rows[].row_jpy`の合計を`total_jpy`と一致させる。過去の助手による概算は履歴のまま保持し、現行価格の根拠にはしない。

現在額を採用するときは、対応する`current_*_scope`に機種・版・`quantity`・`price_basis`・`tax_status`・`shipping_included`と、採用した見積IDだけの`quote_ids`（重複のない空でない配列）を記す。選択した見積は同じ`component`で、機種の集合とすべての条件が範囲に一致する必要がある。その`total_jpy`の合計だけを現在額へ転記する。未選択の相見積は加算しない。数量、単価／ロット総額、税、送料条件の換算は扱わない。異なる条件を比較するときは別の見積として保存し、条件が一致するものを選ぶ。

複数見積を合算する場合は、必要な部品・数量を重複なくカバーする説明を空でない`coverage_note`に記す。選択見積間で同じ`rows[].part`ラベルがあると重複計上として拒否する。ただし、ラベルが違う部品や費用の意味上の重複まで検査では証明できないため、説明と根拠を人が確認する。部品別価格を全体価格に混ぜない。

新しい製作候補は`project/release-state.json`の`candidate_files`にリポジトリ相対`path`とファイルの`sha256`を記録する。従来の`path`・`sha256`だけの項目も有効。候補を版付きで識別するときは、台帳内で一意な空でない`id`と、`component`、`model`または`models`の一方、`revision`を記録する。`model`/`models`は`current-spec.json`の機種キーを使う。`current_lid_manufacturing`は`null`、または`model`/`models`の一方、`revision`、`candidate_ids`（空でなく重複しない候補ID一覧）を持つオブジェクトとする。参照先すべての`component`は`lid`、機種集合と版は現行指定に一致させる。アルミ板とPA12フレームなど複数ファイルで蓋候補を構成するときは、それぞれのIDを一覧にする。参照先のファイル存在とSHA-256も検査する。候補の登録や現行指定だけでは製造承認にならず、`production_approved`、機種別`manufacturing_release`、`release_gate`、G01〜G11を進めない。`engineering/release/`への配置は承認後に限り、`published_release_files`に同じパスとハッシュを記録する。

承認には`approval_record`の承認者・日付・承認ファイル一覧（各パスとSHA-256）・`model_revisions`（機種別の製作版）、G01〜G11すべての`closed`状態、`result.summary`、実在する根拠ファイルの`result.evidence`一覧、`current-spec.json`の`release_gate`および機種別`manufacturing_release`との一致が必要。R8がプレビューだけの間、`latest_preview_is_manufacturing_data`は`false`とする。静的チェックは台帳・ファイル・ハッシュの整合を見るもので、加工適合、強度、現物試験、製造承認そのものを代行しない。
